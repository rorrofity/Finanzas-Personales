# HFS — Saldo único y Salud financiera actualizada

Especificación previa al código: 2026-11-02 America/Santiago. El usuario autoriza implementar las mejoras de Salud, priorizar saldo Fintoc/proyecciones completas/refresco automático, desplegar y actualizar Git, conservando gastos y clasificaciones. Aclara expresamente que toda la aplicación debe usar un único saldo actual de cuenta corriente guardado en la base de datos.

## Contrato

| ID | Requisito verificable |
| --- | --- |
| HFS-01 | El saldo disponible del snapshot bancario CLP guardado por Fintoc (`fintoc_bank_balances.available`) es el único saldo actual de cuenta corriente. Cuenta corriente, Salud y liquidez del Dashboard leen un servicio canónico común. No sumar movimientos otra vez al snapshot, ni usar cartola/saldo inicial/cálculo histórico como saldo actual alternativo. Contable (`current`) pertenece al mismo snapshot y solo es metadata bancaria, no otra fuente. |
| HFS-02 | Conservar todas las tablas y filas existentes: movimientos, categorías, divisiones, notas, identidades, referencias, saldos históricos y banco guardado. No sobrescribir `checking_balances` ni migrar/multiplicar registros para unificar lecturas. Históricos y netos del mes siguen representando flujos, claramente distintos del saldo actual. Ningún reparto se pierde o duplica. Sin cambios de credenciales, horarios o automatizaciones bancarias. |
| HFS-03 | Servicio `getCanonicalCheckingBalance(owner,{query,env,now})`: SELECT puro, filtra dueño y cuenta configurada; sin llamadas al proveedor. DTO `{source:'fintoc',provider:'fintoc',currency:'CLP',amount,available,current,state,freshness,bankUpdatedAt,queriedAt,reason}`; montos string o null, `amount=available`. Estado available/unavailable/error y frescura current/stale/unknown. Cero real y saldo negativo son números válidos; dato ausente/incorrecto/fallo nunca se convierte en cero o saldo antiguo. Snapshot mayor a 24h se marca atrasado; no inventar fecha bancaria con la hora HTTP. |
| HFS-04 | La API `/api/checking/global-balance` conserva `saldo_actual` number/null y agrega el DTO canónico. Dashboard conserva `disponibleHoy` number/null y agrega `checking` canónico. Salud conserva `checking.currentBalance` number/null y expone metadata canónica. Endpoint de saldo Fintoc conserva compatibilidad y utiliza la misma lectura/validación. Lectura de hogar autorizado mantiene mismo saldo; otro espacio no obtiene saldo del titular. |
| HFS-05 | Eliminar de Cuenta corriente la cifra de saldo calculado alternativa y la comparación/diferencia contra cartola. Mantener un único panel de saldo bancario con fecha real, frescura y estados ausente/error. Abonos/cargos del período son flujos históricos y no modifican ese saldo. Mostrar disponible no verificado/último dato conocido cuando corresponda. Dashboard no formatea null como $0. |
| HFS-06 | Resolver proyecciones efectivas con lectura pura: ocurrencias guardadas + plantillas elegibles sin ocurrencia del período. Mantener overrides, inactivas y fechas ajustadas al último día; no resucitar una ocurrencia inactiva como virtual. Incluir ingresos/gastos recurrentes y no recurrentes según inicio/repetición. Salud y computeCommitments usan el mismo resolver/relation que los análisis proyectados pertinentes del Dashboard. Nunca crear ocurrencias por consultar/refrescar Salud o Dashboard. El CRUD explícito existente de Proyectados mantiene sus permisos y datos. |
| HFS-07 | Salud conserva la fórmula de saldo disponible + ingresos previstos − compromisos; tarjetas y cuotas leen padres originales sin multiplicarlos por divisiones. Dinero sumado con unidades mínimas exactas/NUMERIC. Lectura consistente en transacción REPEATABLE READ READ ONLY; errores recuperables por fuente no se convierten silenciosamente en cero. Si falta una fuente necesaria, sus importes dependientes/resultado/evaluación son null o explícitamente parciales. Sin score saludable definitivo con saldo ausente/atrasado, conversiones pendientes, red desconocida u otra cobertura incompleta. Cero de una fuente consultada correctamente sí es cero. |
| HFS-08 | DTO Salud añade `generatedAt`, `sources.{checking,national,international,installments,projected}`, metadata por fuente `{state,freshness,asOf,errorCode}` y sincronización de correos cuando esté disponible. `summary` conserva importes/score/status y añade razones de parcialidad. `checking.lastUpdated` refleja fecha bancaria real, nunca la hora de consulta. Datos desconocidos/fallidos deben quedar visibles como no verificados. Mes del resumen significa compromisos a pagar en el período seleccionado; saldo es la referencia bancaria actual con fecha propia. |
| HFS-09 | Frontend Salud: consulta al entrar/cambiar usuario-hogar-período, al regresar al primer plano/foco, recuperar conexión, finalizar importación/edición, recibir señal push a la ventana; polling cada cinco minutos solamente visible y online. Refresco consulta exclusivamente el backend guardado, no inicia sincronización con banco/N8N. Debounce de eventos simultáneos; AbortController/generación evita respuestas antiguas y cambios de hogar. Background refresh conserva vista útil y muestra error de actualización sin aparentar datos frescos. |
| HFS-10 | Caché explícita de Salud por identidad + hogar + período, con origen y fecha visibles. No esconder 401/403 ni almacenar respuestas tardías en un hogar distinto. Sacar Salud y saldo global del fallback Workbox genérico por URL; datos offline nunca simulan saldo actual confirmado. Eventos financieros compartidos no contienen importes/secretos; no producen bucles de refresco GET. Compartir hook para saldo de Cuenta corriente y liquidez cuando proceda. |
| HFS-11 | Presentación: saldo disponible bancario, compromisos del período y resultado previsto claros; componentes de Visa/Mastercard/proyectados/ingresos verificables y estados por fuente. Mantener claro/oscuro, móvil sin scroll lateral, lectura de pareja y permiso de escritura. Bloquear score definitivo y mostrar por qué un resumen es parcial. Como primera entrega, próximos compromisos pueden derivarse de fechas conocidas; no inventar vencimientos de tarjeta ni marcar pagado por inferencia. Conciliación de pagos/proyecciones y pronóstico diario requieren evidencia/contrato adicional antes de cambiar datos. |
| HFS-12 | SDD→TDD RED observado antes del código: servicio canónico, todos consumidores, resolver puro, errores y frescura, refresco/caché/carreras, UI/temas. PostgreSQL/HTTP temporal verifica doce plantillas faltantes incluidas sin DML, saldo idéntico en tres vistas y permisos/aislamiento/snapshot. Playwright con fixtures local para saldo/refresco/unknown/partial y regresión existente; no debilitar pruebas previas, adaptar expectativas de saldo alternativo explícitamente retirado. |
| HFS-13 | Desplegar código/build probado al servidor. Sin migraciones o escrituras financieras necesarias. Respaldo privado y huellas antes/después incluyendo once tablas originales, dos tablas de divisiones y snapshot de saldo. Verificación productiva solo fechas, estados, recuentos, comparaciones/digests internos y códigos HTTP; no exportar importes ni crear datos reales de prueba. No llamar GET Proyectados como dueño para probar (comportamiento legado materializa). Conservar assets anteriores, programaciones/respaldos/N8N. Repo y servidor en el mismo commit final. |

## Compatibilidad y decisiones

No existen dos saldos actuales de negocio: Fintoc alimenta una referencia bancaria ya persistida. Se retiran consumidores legacy que confundían una cartola histórica con saldo actual. La tabla histórica se conserva como evidencia para conciliación, sin hacerla competir visualmente con el banco.

No se cambia la frecuencia Fintoc diaria de las 07:00 ni la de correos cada hora 08:00–00:00. Refrescar la vista no hace más consultas al banco. Se conserva el único snapshot disponible marcado con su antigüedad; no se fabrica uno nuevo a partir de gastos.
